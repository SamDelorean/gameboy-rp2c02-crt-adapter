# Aspect-Correct Scaling

## Design objective

Version 1 should preserve the original Game Boy image proportions rather than stretching the 160 x 144 source image across the full 256 x 240 PPU raster.

The target presentation is therefore:

```text
PPU active raster: 256 x 240

11 border | 234-pixel Game Boy image | 11 border
          x 240 lines high
```

In version 1 the two border regions are fixed black. The Game Boy picture fills the available height while these narrow side regions absorb the remaining horizontal space.

This is now the baseline presentation algorithm.

## Why 234 x 240

The DMG logical image is:

```text
160 x 144
```

Its logical aspect ratio is:

```text
160 / 144 = 10 / 9
```

The NTSC RP2C02 raster is not composed of square display pixels. Using the working NES NTSC pixel-aspect model of approximately 8:7, a 240-line-tall Game Boy picture with preserved geometry ideally occupies:

```text
160 x (240 / 144) x (7 / 8)
= 233.333... PPU dots
```

The nearest convenient integer width is 234 dots.

This leaves:

```text
256 - 234 = 22 dots
```

or 11 border dots on each side.

The resulting geometry error is intentionally tiny and is much smaller than stretching the image to the full 256-dot width.

The exact appearance on a physical CRT will still depend on that set's horizontal size and overscan adjustments; the digital algorithm remains fixed.

## Vertical scaler: 144 -> 240

The vertical relationship remains exact:

```text
240 / 144 = 5 / 3
```

Use the simple periodic repetition pattern:

```text
source lines: L0 L1 L2
repeat:        2  1  2
output:       L0 L0 L1 L2 L2
```

Repeat this 48 times:

```text
48 x 3 = 144 source lines
48 x 5 = 240 output lines
```

No interpolation or filtering is required.

## Horizontal scaler: 160 -> 234

The horizontal scaler preserves every original source pixel value and only duplicates selected pixels.

A 160-pixel source line must produce 234 image dots:

```text
160 original emissions + 74 duplicated emissions = 234
```

Therefore each source pixel is emitted either once or twice.

A simple integer error accumulator is sufficient:

```text
error = centered_initial_phase

for each of 160 source pixels:
    emit pixel once
    error += 74

    if error >= 160:
        emit the same pixel a second time
        error -= 160
```

The accumulator phase should be chosen so the duplicate distribution is visually centered. The exact initial phase is an implementation detail, but the mapping must be deterministic and symmetric enough that no visible horizontal bias is introduced.

An equivalent center-sampled reference mapping for tests is:

```text
source_x = floor((output_x + 0.5) * 160 / 234)
```

for `output_x = 0..233` inside the active Game Boy picture.

This mapping produces:

- 86 source pixels emitted once;
- 74 source pixels emitted twice;
- 234 total output dots.

Because `gcd(160, 234) = 2`, the distribution can also be represented as a fixed 80-source-pixel -> 117-output-dot pattern repeated twice per line.

## Complete line generation

The output state machine for each visible PPU line is conceptually:

```text
emit border for 11 dots
emit one scaled 160-pixel Game Boy line as 234 dots
emit border for 11 dots
```

Total:

```text
11 + 234 + 11 = 256 dots
```

The two side regions are generated by the output state machine. They are not stored in the 160 x 144 framebuffer.

## Border / frame generator integration

The 11-dot side regions are not a separate workaround attached to the scaler. They are the version-1 use of the project's **border/frame generator**.

Conceptually:

```text
border generator     scaled Game Boy picture     border generator
      11 dots                 234 dots                 11 dots
          \______________________|______________________/
                                 |
                            256-dot line
```

For version 1:

```text
border_mode = fixed black
```

The scaler is responsible only for converting the 160 source pixels into the 234 image dots. The border generator is responsible for the remaining 22 raster positions.

This separation is deliberate. A future firmware revision may use the same border generator for simple alternatives such as:

- a fixed user-selected border color;
- a color derived from the active palette;
- another low-complexity static or deterministic border effect.

Such future behavior must not require changing the 160 -> 234 scaling algorithm, rewriting the source framebuffer, or adding a general-purpose graphics layer.

Version 1 exposes no border-selection control: both side regions remain fixed black.

## Framebuffer rule

The baseline still stores only the original Game Boy image:

```text
160 x 144 x 2 bits = 5,760 bytes per frame
```

Two source buffers remain sufficient for ping-pong capture/display ownership:

```text
11,520 bytes total
```

There is no required 234 x 240 or 256 x 240 framebuffer.

Scaling and border generation happen while reading the front buffer for EXT output.

## Palette interaction

Scaling operates only on the 2-bit DMG shade index.

It does not know or care which visible colors are selected. Manual palettes and optional SGB-derived palettes therefore require no change to the scaling algorithm.

The border generator is also logically separate from the four Game Boy shade values. In version 1 it emits a dedicated safe black value. A future documented revision may deliberately choose another border color or effect without changing the stored Game Boy image.

## Design rationale

This algorithm was selected because it satisfies the project goals simultaneously:

- preserves the Game Boy's image proportions;
- fills the CRT vertically;
- uses only small side borders;
- avoids visibly stretching the Game Boy image to 4:3;
- requires no interpolation;
- requires no floating point;
- requires no general-purpose scaler;
- requires no scaled framebuffer;
- leaves a clean, low-cost border-generation hook for future cosmetic options;
- can be generated with a tiny deterministic integer state machine, lookup table, DMA pattern, PIO program, or equivalent hardware-assisted logic.

The project intentionally does not add alternate scaling modes in version 1. Aspect-correct output with fixed-black side borders is the baseline behavior.
